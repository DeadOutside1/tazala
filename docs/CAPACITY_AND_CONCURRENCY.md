# Руководство по архитектуре, нагрузке и логированию Tazala

В данном документе зафиксированы архитектурные параметры сервиса **Tazala**, его текущая пропускная способность, профиль одновременных пользователей (concurrency), механизмы логирования ошибок и план масштабирования при росте аудитории.

---

## 1. Пропускная способность и одновременные пользователи

Сервис имеет два принципиально разных уровня нагрузки:

### А. Легкие операции (Бот, Меню, Кнопки, Выбор языка, Отправка отзыва)
* **Одновременных пользователей:** **от 500 до 1 500+ онлайн**
* **Время отклика:** **2–5 миллисекунд**
* **Архитектурный базис:**
  * Фреймворк **Aiogram 3** на базе асинхронного цикла событий Python (`asyncio`).
  * In-memory хранилище **Redis** (ключи FSM, настройки языков, счетчики метрик).
  * Любое нажатие inline-кнопки или команды обрабатывается без блокирующих вызовов.

### Б. Тяжёлые операции (Вход по QR/SMS, Сканирование диалогов, Очистка сообщений, Папки)
* **Одновременно в одну секунду (Single-Server, 2 vCPU / 2–4 GB RAM):** **25–50 активных сессий**
* **Пропускная способность в сутки:** **от 3 000 до 8 000+ уникальных пользователей** (при естественном распределении обращений в течение дня).

## 2. Узкие места и встроенные механизмы защиты

| Фактор | Причина | Реализованная защита в Tazala |
| :--- | :--- | :--- |
| **Оперативная память (RAM)** | Каждый активный процесс авторизации или сканирования поднимает изолированный клиент Telethon (`15–25 МБ RAM` на сессию). | Сессия автоматически уничтожается после выхода (`log_out`), память освобождается. TTL сессии в Redis ограничен 5–30 мин. |
| **Лимиты Telegram к IP сервера (`FloodWaitError`)** | Telegram защищает свои дата-центры от спама. Если с 1 IP сервера отправлять тысячи вызовов API в секунду, Telegram накладывает временный троттлинг. | Встроен класс `FloodSafeExecutor` ([`throttle.py`](file:///backend/app/telegram/throttle.py)), который делает микропаузы (0.5 сек) и экспоненциальный откат, защищая IP сервера и аккаунты пользователей. |
| **Защита от параллельного спама** | Пользователь может многократно кликать «Очистить» или «Сканировать». | `RedisLock` блокирует параллельные одинаковые действия на уровне конкретного `user_id` (`scan:{user_id}`, `clean:{user_id}`). |

## 3. Архитектура логирования: Отзывы vs Системные ошибки

### 📝 Хранилище отзывов (`reviews.jsonl` и Redis)
* **Назначение:** Сохранение обратной связи от реальных пользователей (1–5 звёзд + текстовый комментарий).
* **Принцип 1 пользователь = 1 отзыв:** Если пользователь меняет оценку, `ratings_sum` корректируется, а `ratings_count` не завышается.
* **Безопасность вывода:** 
  * Комментарии обрезаются до `150` символов (`comment[:150]`), предотвращая превышение лимита Telegram в 4096 знаков.
  * Все специальные символы Markdown (`_`, `*`, `` ` ``, `[`) автоматически экранируются (`_escape_md`), предотвращая сбои парсера Telegram.

### ⚠️ Системные логи и перехват ошибок
* **Назначение:** Технический аудит работы MTProto, 2FA, авторизации и очистки.
* **Где смотреть:**
  * Локальный запуск: консоль Uvicorn / stdout.
  * Docker-окружение: `docker compose logs -f backend`.
* **Защита UI:** При возникновении исключений бот не падает, а выводит безопасные текстовые сообщения без Markdown-форматирования (`parse_mode=None`).

## 4. План масштабирования при вирусном росте (10 000+ пользователей онлайн)

Если бот получает взрывной приток трафика из соцсетей (TikTok, Instagram Reels, Stories), масштабирование выполняется по следующему плану:

1. **Очередь фоновых воркеров (Celery / ARQ / Redis Streams):**
   * Тяжёлые операции сканирования и очистки отделяются от процесса Telegram-бота.
   * Пользователю выводится статус: *«Вы в очереди №3, запуск через 5 сек»*.
   * Сервер работает с фиксированным пулом воркеров и никогда не падает от перегрузки памяти.
2. **Переход с Long Polling на Webhooks:**
   * Telegram напрямую шлёт обновления в FastAPI эндпоинт бота по HTTPS.
   * Пропускная способность увеличивается в 10–20 раз.
3. **Пул исходящих прокси (MTProto Proxies):**
   * Подключения к дата-центрам Telegram распределяются через ротируемые IP-адреса, полностью снимая лимиты на единый IP сервера.
